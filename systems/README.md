# Systems-Under-Test Directory

Stores the source code and deployment configs of the memory systems under test.

## MindMemOS

**Run mode**: Docker infrastructure + FastAPI server (HTTP communication)

### Files that need config

| File | Description | Action |
|------|------|------|
| `LifeBench_eval/.env` | global API Key | fill in LLM_API_KEY, VECTORIZE_API_KEY, etc. |
| `systems/MindMemOS/.env` | Docker container connection parameters | copy from `.env.example`, modify as needed |
| `systems/MindMemOS/config/mindmemos/dev.yaml` | server config | copy from `dev.example.yaml`, modify as needed |
| `config/systems/mindmemos.yaml` | pipeline parameters | normally no change needed; optionally adjust memory_algorithm, search_top_k, etc. |

The Builder automatically generates the API key and writes it to `config/mindmemos/api_keys.yaml`; no manual handling needed.

### Services that need starting

The Builder ([src/builders/mindmemos_builder.py](../src/builders/mindmemos_builder.py)) automatically handles the following startup flow:

1. **Docker infrastructure** — Qdrant (vector DB, port 6333), Neo4j (graph DB, ports 7474/7687), Kafka (message queue, port 9092)
2. **NLP asset installation** — installed via `scripts/install_nlp_assets.py`
3. **API Server** — `uvicorn mindmemos.api.app:app --host 127.0.0.1 --port 8000`

### Manual startup (fallback when the Builder fails)

```bash
# 1. start the Docker services
docker compose --env-file systems/MindMemOS/.env \
  -f systems/MindMemOS/dockers/docker-compose.memory.yml \
  up -d --wait qdrant neo4j kafka kafka-ui kafka-exporter

# 2. start the API Server
cd systems/MindMemOS
.venv/Scripts/python.exe -m uvicorn mindmemos.api.app:app --host 127.0.0.1 --port 8000
```

### Core flow

The Adapter ([src/adapters/mindmemos_adapter.py](../src/adapters/mindmemos_adapter.py)) communicates with the API Server via `mindmemos_sdk`:

- **ADD** → `POST /v1/memory/add`, batch-written per session
- **SEARCH** → `POST /v1/memory/search`, supporting two strategies: agentic (multi-hop graph search) and fast (vector search)
- **ANSWER** → the Adapter's built-in LLM call (prompt consistent with mindmemos_eval), no second retrieval

The memory algorithm is switched via `memory_algorithm` in `config/systems/mindmemos.yaml`:
- `vanilla` — flat memory + vector search
- `schema` — entity modeling + graph + agentic multi-hop search

## Hindsight

**Run mode**: purely local in-process (no Docker, uses the embedded pg0 database)

### Files that need config

| File | Description | Action |
|------|------|------|
| `LifeBench_eval/.env` | global API Key | fill in LLM_API_KEY, VECTORIZE_API_KEY, etc. |
| `systems/hindsight/.env` | Hindsight environment variables | can be empty; the Builder injects all env vars from YAML |
| `config/systems/hindsight.yaml` | pipeline parameters | modify LLM provider/model, embedding provider, etc. as needed |

Hindsight's environment variables are injected by the Builder ([src/builders/hindsight_builder.py](../src/builders/hindsight_builder.py)) from the YAML config, not via the `.env` file. To run Hindsight itself manually (not through the pipeline), configure `systems/hindsight/.env` (refer to `.env.example`).

### Services that need starting

**No external service needs starting.** The Builder creates the `MemoryEngine` instance in-process and automatically manages the lifecycle of the embedded pg0 database.

### Core flow

The Adapter ([src/adapters/hindsight_adapter.py](../src/adapters/hindsight_adapter.py)) calls `MemoryEngine` directly:

- **ADD** → `memory.retain_batch_async()` — batch-written grouped by conversation
- **SEARCH** → `memory.recall_async()` — multi-strategy retrieval (semantic + BM25 + graph + temporal) + reranking
- **ANSWER** → an independent LLM call using structured output (`QuestionAnswer` pydantic model)

Key config items (in `config/systems/hindsight.yaml`):

| Parameter | Default | Description |
|------|--------|------|
| `budget` | `mid` | retrieval candidate scale: low(~100) / mid(~300) / high(~1000) |
| `db_url` | `pg0` | database: pg0 is embedded; an external PostgreSQL can also be configured |
| `memory_llm_*` | deepseek-v4-flash | LLM for memory extraction/consolidation |
| `answer_llm_*` | same as memory | LLM for answer generation |
| `HINDSIGHT_API_EMBEDDINGS_*` | SiliconFlow | vectorization service config |
| `HINDSIGHT_API_RERANKER_*` | SiliconFlow | reranking service config |

## Cognee

**Run mode**: purely local in-process (no Docker, uses SQLite + LanceDB + Ladybug file storage)

### Files that need config

| File | Description | Action |
|------|------|------|
| `LifeBench_eval/.env` | global API Key | fill in LLM_API_KEY, VECTORIZE_API_KEY, etc. |
| `systems/cognee/.env` | Cognee environment variables | auto-generated by the Builder, no manual creation needed |
| `config/systems/cognee.yaml` | pipeline parameters | modify LLM, Embedding, retrieval strategy, etc. as needed |

The Builder ([src/builders/cognee_builder.py](../src/builders/cognee_builder.py)) translates the YAML config into `systems/cognee/.env` on every run; the cognee SDK loads that file to get its config. **No need to manually edit `systems/cognee/.env`**.

### Services that need starting

**No external service needs starting.** Cognee uses file storage:
- **SQLite** — metadata and state storage
- **LanceDB** — vector embedding storage
- **Ladybug** — knowledge graph storage

All data defaults to `D:/cg/data/` and `D:/cg/system/` (changeable via `data_root_directory` and `system_root_directory` in `config/systems/cognee.yaml`).

### Core flow

The Adapter ([src/adapters/cognee_adapter.py](../src/adapters/cognee_adapter.py)) calls the cognee SDK directly, replicating the BEAM eval flow:

- **ADD** → `cognee.add()` + `cognee.cognify()` — first write raw data, then run the 5-task pipeline (classify → chunk → extract graph → summarize → store)
- **SEARCH** → `cognee.search(query_type=GRAPH_COMPLETION, only_context=True)` — graph traversal + context retrieval (no LLM completion)
- **ANSWER** → `cognee.generate_completion()` — LLM completion over the cached graph context

**Performance note**: the cognify stage includes LLM entity/relation extraction and takes a long time. For session-only dates that won't be searched (no QA), the pipeline automatically skips cognify and only runs add.

Key config items (in `config/systems/cognee.yaml`):

| Parameter | Default | Description |
|------|--------|------|
| `retriever_type` | `graph_completion` | retrieval strategy: supports graph_completion / graph_completion_cot / graph_summary_completion, etc. |
| `top_k` | 40 | number of memories finally returned |
| `wide_search_top_k` | 100 | wide-search candidate pool size |
| `chunk_size` | 1024 | cognify chunk token budget |
| `enable_backend_access_control` | true | multi-tenant data isolation (per-user independent Ladybug graph file) |
| `prune_on_init` | false | clear state before each run (should be true for benchmarking) |
| `sqlite_timeout` | 300 | SQLite concurrent-write timeout (seconds) |

## Mem0

**Run mode**: Docker infrastructure + HTTP API (OSS Server)

### Files that need config

| File | Description | Action |
|------|------|------|
| `LifeBench_eval/.env` | global API Key | fill in LLM_API_KEY, VECTORIZE_API_KEY, RERANK_API_KEY, etc. |
| `systems/mem0/server/.env` | Docker container env vars | auto-generated by the Builder from `.env` and YAML, no manual creation needed |
| `config/systems/mem0.yaml` | pipeline parameters + runtime_config | modify LLM/Embedder provider, model, etc. as needed |

The Builder ([src/builders/mem0_builder.py](../src/builders/mem0_builder.py)) auto-generates `systems/mem0/server/.env` from `LifeBench_eval/.env` and the YAML's `runtime_config` block, and after starting the containers pushes the runtime LLM/Embedder config to the mem0 server via `POST /configure`. **No need to manually edit `systems/mem0/server/.env`**.

### Services that need starting

The Builder automatically handles the following startup flow:

1. **PostgreSQL** — Docker container, pgvector extension for vector storage (port 5432)
2. **Mem0 OSS Server** — Docker container, FastAPI service (port 8888)
3. **Mem0 Dashboard** — Docker container, optional Web UI

### Manual startup (fallback when the Builder fails)

```bash
cd systems/mem0/server

# 1. prepare .env (generate referencing LifeBench_eval/.env and config/systems/mem0.yaml)
cp .env.example .env
# edit .env, fill in the LLM/Embedding API Key

# 2. start the service
docker compose -f docker-compose.yaml up -d --wait

# 3. verify the service
curl http://localhost:8888/configure
```

### Core flow

The Adapter ([src/adapters/mem0_adapter.py](../src/adapters/mem0_adapter.py)) communicates with the Mem0 OSS Server via HTTP:

- **ADD** → `POST /memories` — written concurrently by batch (default 4 messages per group), with an `infer` switch controlling whether the LLM extracts facts
- **SEARCH** → `POST /search` — vector search + Cohere-compatible reranker (SiliconFlow), isolated by user_id
- **ANSWER** → the Adapter's built-in independent LLM call (7-step reasoning prompt), no second retrieval

Key config items (in `config/systems/mem0.yaml`):

| Parameter | Default | Description |
|------|--------|------|
| `mode` | `oss` | run mode: oss (local Docker) / cloud (Mem0 Cloud API) |
| `infer` | `true` | whether the LLM extracts facts (false stores text as-is) |
| `add_batch_size` | 4 | number of messages merged per API call (lets the LLM see multi-turn context) |
| `add_concurrency` | 5 | concurrency in the ADD stage |
| `runtime_config.llm` | deepseek | LLM provider / model / base_url (pushed via /configure) |
| `runtime_config.embedder` | openai_compatible + SiliconFlow | Embedder provider / model / dimensions |
| `search.top_k` | 40 | number of memories returned by retrieval |
| `search.rerank` | false | whether to enable server-side rerank (configured inside the mem0 server) |

**Performance note**: Mem0 runs as Docker containers; the first cold start needs to pull images + initialize PostgreSQL (about 30-60s). The pgvector data volume persists across container restarts; old data needs manual cleanup or enabling the `prune` feature.

## Comparison of the four systems

| Dimension | MindMemOS | Mem0 | Hindsight | Cognee |
|------|-----------|------|-----------|--------|
| Run mode | Docker + HTTP API | Docker + HTTP API | in-process direct call | in-process direct call |
| External dependencies | Qdrant, Neo4j, Kafka | PostgreSQL(pgvector) | none | none |
| Storage | Qdrant(vector) + Neo4j(graph) | pgvector(vector) + PostgreSQL | pg0(embedded PG) | SQLite + LanceDB + Ladybug |
| ADD cost | low (write API) | low (write API, optional LLM extraction) | medium (LLM fact extraction) | high (cognify 5-task pipeline) |
| Search strategy | fast / agentic multi-hop | vector search + rerank | semantic+BM25+graph+temporal | GRAPH_COMPLETION graph traversal |
| Startup time | ~30-90s (Docker + service) | ~30-60s (Docker) | <5s | <5s |
