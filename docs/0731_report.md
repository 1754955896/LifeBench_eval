# memU 记忆系统

## memU 核心思想

memU 将记忆视为一个**自驱动的文件系统**，能够自动响应用户交互——当用户输入数据时，系统自动提取相关信息、修改现有文档、生成新文件，并组织整个结构。

memU 采用**三层渐进式抽象架构**，将异构输入数据逐级转化为可查询、可理解的文本记忆：

| 层级 | 名称 | 说明 |
|------|------|------|
| **L0** | **Resource Layer（资源层）** | 原始数据层，存储完整的原始输入（文本、图像、语音、视频、对话、代码等），保证完整性和可追溯性 |
| **L1** | **Memory Item Layer（记忆单元层）** | 从原始资源中提取的最小粒度记忆单元，每个单元为自然语言句子，描述一个明确的事实、事件或状态 |
| **L2** | **Memory Category Layer（记忆分类层/文件层）** | 将零散记忆单元按主题聚合为结构化文件（如“用户画像”、“生活事件”、“工作日志”等），最终送入 Agent 上下文用于推理决策 |

这三层之间保持**完整可追溯关系**：从原始数据 → 记忆单元 → 聚合分类，可双向追踪每条知识的来源与演化过程。

| 时间  | Memos | memU |
|------|:----:|:----:|

### ADD 阶段延迟对比

| 统计项 | Memos | memU | 
|--------|:----:|:----:|
| **平均延迟** | **81.10s** | **6.19s** | **13.1x** |
| **中位延迟（P50）** | **69.45s** | **4.68s** | **14.8x** |
| **P95** | 164.13s | 15.23s | 10.8x |
| **P99** | 379.29s | 21.93s | 17.3x |
| **最小延迟** | 9.34s | 0.66s | 14.2x |
| **最大延迟** | 427.36s | 104.37s | 4.1x |

- **Memos**：延迟和消息数正相关（5 条消息约 29s，50 条消息约 399s），长尾严重（P99 达 379s）。
- **memU**：延迟稳定在 4-9s 区间，与消息数无关，P99 仅 21.9s。

# EverMemOS 记忆系统

## 1. 实验结果对比

在 LoCoMo 数据集的前 2 个 conversation（233 个 QA，40 个 session）上，两个版本的评测结果如下：

### 1.1 准确率对比

| 版本 | 准确率 | 正确数/总数 |
|------|--------|-------------|
| **Native 版** | **84.55%** | 197 / 233 |
| **HTTP API 版 (Server)** | **80.69%** | 188 / 233 |

### 1.2 耗时对比

| 版本 | 总耗时 | Add+Search 耗时 |
|------|--------|-----------------|

| **HTTP API 版** | ~94 min (5644s) | ~75 min(4525s)|

## 2. 方法差异

### 2.1 系统架构与部署

| 维度 | Native 版 | HTTP API 版 |
|------|-----------|-------------|
| 调用方式 | 直接 import Python 模块 | HTTP API → FastAPI 服务 |
| 基础设施 | **零依赖**（无 Docker） | 需 Docker + MongoDB + ES + Milvus + Redis |
| 启动耗时 | **~1s**（仅 venv 检查） | ~225s（Docker 45s + API 180s） |

**关键点**：Native 版通过直接 import 绕过了完整的微服务栈，将分布式存储（MongoDB/ES/Milvus）替换为本地文件（`.pkl`），大幅降低了部署门槛和启动时间。

### 2.2 记忆处理与边界检测

| 维度 | Native 版 | HTTP API 版 |
|------|-----------|-------------|
| 边界检测 | **无**（全量一次性提取） | **有**（LLM 判断事件边界，Redis 排队） |
| 处理方式 | 批量缓冲 → 最终日期触发 | 实时流式逐条摄入 |
| 时间感知 | 存在“未来信息泄露”风险 | 严格时序，无泄露 |

**关键点**：这是两者**最核心的方法论差异**。HTTP API 版逐日摄入、逐日检索，保证“不看到未来数据”。Native 版则将所有消息缓冲到最后一次性处理，没有边界检测相比环节。

### 2.3 检索策略

| 维度 | Native 版 | HTTP API 版 |
|------|-----------|-------------|
| Agentic 检索 | **简化版**（无多轮、无充分性判断） | **完整版**（Round1→Rerank→判断→Round2） |
| 检索来源 | 本地 `.pkl` 文件 | ES + Milvus 生产索引 |
| Rerank |  逻辑相同 | 逻辑相同 |
